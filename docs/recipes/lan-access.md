# レシピ: LAN アクセス（組み込み Web サーバ、M6）の運用

作成日: 2026-10-08（README「LANアクセス」から切り出し。トラックB＝アプリ作者向け）

デフォルトは無効（`invoke()`専用、攻撃面ゼロ）。設定画面から有効化すると、
同一LAN内の他端末のブラウザから同じ管理画面をREST API + SSEで利用できる
（仕様 §11）。本書は有効化・閲覧公開・開発用バイナリ・セキュリティ注意・
TLS 終端・PWA の運用手順をまとめる。構成図は
[architecture-overview.md §2](../architecture-overview.md)、起動・ログイン・閲覧公開の
フローは [architecture-flows.md](../architecture-flows.md)。

## 有効化手順

1. デスクトップアプリの設定画面 →「LANアクセス（組み込みWebサーバ）」で
   トグルをON、バインドアドレス（`0.0.0.0`でLAN公開）・ポート番号を設定し
   「保存して適用」。
2. 表示されたURL/QRコードから、同一LAN内の他端末のブラウザでアクセスし、
   初回起動時（Tauriウィンドウまたはこのブラウザ自身）に作成した
   管理者アカウントでログイン。まだアカウントがなければ初回セットアップ
   画面が表示される。

### 起動時にポートが使用中だったとき

LAN アクセスを ON のままアプリを起動したとき、保存したポートがほかのプロセスに
使われていたら、**そのすぐ後ろの決まった範囲（保存したポート +1〜+19、65535 まで）**
から空いているポートを順に選んで起動する。

- 選んだポートは設定に**保存**され、次回からはそのポートで起動する（起動のたびに
  変わると、他端末のブックマークや QR コードが使えなくなるため）。設定画面の URL・
  QR コードも新しいポートを示す。管理者には「8721 が使用中のため 8722 で起動しました」
  の趣旨の通知が出る。この変更は監査ログに `settings_change`（操作者なし、
  `detail.reason: "portInUse"`）として残る。
- ポート 0 による OS 任せの割り当てやランダムなポートは使わず、保存したポートの後ろの
  決まった範囲だけを試す（範囲は保存したポートからの相対なので、49151 などを保存して
  いれば OS の一時ポートの範囲に入ることはある）。待受アドレス（バインドアドレス）は
  変えない。
- 範囲内に使えるポートが無ければ、従来どおり起動せず、保存したポートが使用中だった旨を
  通知する（すべて使用中か、OS の予約などで使えないポートが含まれていたかを区別する）。権限不足・アドレスが無いなど、使用中以外の失敗では別のポートを試さない。
- 設定画面で「保存して適用」したときは自動では選ばない（指定したポートが使用中なら
  エラーになり、元の設定に戻る）。

### 設定画面に出る値（保存値と稼働値）

設定画面（`server_status`）は、**保存した設定**と**いま待ち受けているサーバーの
実際の値**を分けて返す（Issue #459）。

- フォームの初期値（有効・バインドアドレス・ポート・閲覧公開）は保存した設定
  （次回の起動で使う値）。
- 状態の表示と URL・QR コードは、稼働中のサーバーが実際に bind したアドレスと
  ポート（`live`）から作る。停止中は URL・QR を出さない。保存したポートの保存に
  失敗した起動時の自動選択などで両者が違うときも、URL・QR は答えるサーバーを指す。
- 両方を同じロックの中で読むので、「保存して適用」と同時に読んでも新旧が混ざらない。
  返す `generation` は適用のたびに変わる。表示した値やコピーした値は、`generation`
  が変わったら読み直す。
- 「保存して適用」が失敗したときは `applyFailure` に、理由（ポート使用中・それ以外の
  bind の失敗・保存の失敗）と、元のサーバーを元のアドレスとポートで戻せたか
  （戻せなければ停止中）が入る。次に適用が成功すると消える。
- `server.*` の設定は「保存して適用」（`server_apply`）でだけ変わる。汎用の
  `settings_set` は `server.` で始まるキーを拒否する（`auth.` と同じ扱い）。

### ファイアウォールの許可に必要な情報（Windows）

別の端末から接続できないときは、設定 > サーバ・接続の「ファイアウォールの許可に
必要な情報」を使う（Issue #219 段階 1。アプリはファイアウォールを変更せず、
昇格もしない）。

- 出る内容: 実行ファイルの絶対パス、通信方向（受信）、プロトコル（TCP）、
  待ち受け中のポート、ネットワークプロファイル（プライベート）、接続元の範囲
  （`LocalSubnet` = この PC のすべてのネットワーク接続のサブネット。VPN を含む）。
  どれも**稼働中のサーバーの値**（`live`）から作り、未保存のフォームの値や
  保存値は使わない。各項目はコピーできる。
- 管理者向けのコマンド: 同じ内容の `New-NetFirewallRule` を 2 つの形でコピーできる。
  管理者として起動した PowerShell で**どちらか 1 つ**を実行する（または管理者に渡す）。
  - 実行ファイル単位（`-Program`）: このアプリが待ち受ける TCP ポートすべてが対象。
    ポートを変えても作り直さなくてよいが、許可の範囲は広い。
  - ポート単位（`-LocalPort`）: そのポートで待ち受けるプログラムすべてが対象。
    ポートを変えたときは、下の「既存のルールがあるとき」の手順で古いルールを直す。
  - どちらのコマンドも、形ごとに決まった `-Name`（`<identifier>.lan.tcp.program` /
    `<identifier>.lan.tcp.port`。ポート番号は含めない）で作る。`New-NetFirewallRule` は
    `-Name` を省くと毎回ランダムな名前の新しいルールを作り、`-DisplayName` や
    `-Group` では重複を防げないため、決まった名前にしている。
  - コマンドは「同じ名前のルールが既にあれば、**何も変えずに**警告を出して止まり、
    無ければ作る」1 行になっている:

    ```powershell
    $n = '<name>'; if (Get-NetFirewallRule -Name $n -ErrorAction SilentlyContinue) { Write-Warning '...' } else { New-NetFirewallRule -Name $n ... }
    ```

    既存のルールを消したり書き換えたりはしない。同じ名前のルールは、管理者が Block に
    変えた・接続元を狭めた・同じ identifier の別インストールの exe を指している、
    ということがあり得るため、名前だけを手がかりに消すと管理者の設定を壊す
    （消してから作る形だと、作成に失敗したときに旧ルールも失う）。

  - 既存のルールがあるとき（ポートを変えた・形を切り替えた・警告が出た）: 管理者が
    `Get-NetFirewallRule -Name '<name>' | Format-List`（ポートや exe は
    `| Get-NetFirewallPortFilter` / `| Get-NetFirewallApplicationFilter`）で中身を
    確かめてから、自分で更新・削除する。不要なら `Remove-NetFirewallRule -Name '<name>'`
    で消してから、画面のコマンドを実行し直す。この削除は画面のコピーするコマンドには
    含めない。
  - ルール名（`-DisplayName`・`-Name`）とグループ（`-Group`）は `tauri.conf.json` の
    `identifier` から作る（派生アプリどうしで衝突しない。リネーム時に
    `identifier` を変えること）。
- コピーの直前に状態を読み直し、表示していたポート・アドレス・実行ファイル
  （`generation`）と変わっていたらコピーせずに表示を更新する。適用中はコピーできず、
  適用や新しい読み直しの後に届いた古い応答（読み直しの順番が古い、または
  `generation` が表示中より小さい）は、表示にもコピーにも使わない。
- 停止中、または待受が loopback（`127.0.0.0/8`）だけのときは「設定は不要」と表示し、
  コマンドは出さない。IPv6 の待受と Windows 以外では出さない。
- 許可しても届かないことがある: 遮断のルールは許可より優先される（初回の
  Windows の通知で許可しなかった場合など）。独自のファイアウォールを持つ
  セキュリティソフトや、集中管理（GPO）された PC では、Windows の許可だけでは
  通らないことがあるので、上の情報を製品の設定や管理者に渡す。Windows の
  ルールの優先順位は [Microsoft の説明](https://learn.microsoft.com/en-us/windows/security/operating-system-security/network-security/windows-firewall/rules)、
  ESET の例は [ESET Smart Security Premium のファイアウォールの基本設定](https://help.eset.com/essp/18/en-US/idh_config_epfw_basic_group.html)
  （版・モードで挙動が変わる）を参照。

#### Windows ファイアウォールの状態（読み取りだけ）

同じ欄の「Windows ファイアウォールの状態」は、上のコマンドで作るルールが
Windows ファイアウォールにあるかを、**昇格せず読み取りだけで**確かめて表示する
（Issue #219 段階 1 の PR-B。ファイアウォールは変更しない）。開いたとき・適用で
待ち受けが変わったとき・「再確認」を押したときに読み直す。

- 調べるのは決まった名前（`<identifier>.lan.tcp.program` / `.port`）のルールだけ。
  照合するのは **ActiveStore（各ストアを合わせた、効く候補のルール）にある、その名前の
  ルール**の値で、ローカルのストアのルールは補足として出す。集中管理（グループポリシー
  など）が同じ名前のルールを配っていると、ActiveStore ではそちらが選ばれ、ローカルの
  ルールの値は適用されないため。
- **ActiveStore にあることは、適用されていることと同じではない。** ActiveStore の
  ルールの `EnforcementStatus` を読み、`Full` のときだけ「適用されています」と出す。
  `InactiveProfile`（今のネットワークプロファイルでは使われない）、
  `LocalFirewallRulesDisallowed`（ポリシーがローカルのルールを許さない）、
  `CategoryOff`（別のファイアウォール製品が有効）など、仕様にあるほかの値は
  「存在するが適用されていません（理由: 値の名前）」と出す。ルールの中身がコマンドの
  内容と一致していて適用状態だけがこれらのときは「期待と違う」ではなく、専用の見出し
  「あり（内容は期待どおり。ただし Windows ファイアウォールとしては適用されていません）」
  にする（作り直しに誘わない。#479）。`CategoryOff` のときは、別の製品（ESET など）が
  Windows のルールも参照して通信が届くことがあるため、「別の端末からの接続確認」で
  確かめ、届かなければその製品の設定で許可する、と添える。中身の違う項目が 1 つでも
  あれば、適用状態もその項目に並べた「期待と違う」のままにする。
  値が読めない・仕様に無い値（新しい Windows など）は「適用状態は不明」とし、値が
  期待どおりでも「期待どおり」とは出さない。形ごとに次のどれかを出す。
  - **ルール無し**: その名前のルールが、効いているルールにもローカルのストアにも無い。
  - **あり（期待どおり）**: ActiveStore のルールが、画面のコマンドが作る内容（受信・
    許可・TCP・プライベート・`LocalSubnet`、実行ファイル単位は exe のパスが今の実行
    ファイルと同じ・ポートは `Any`、ポート単位はポートが待ち受け中のポートと同じ・
    プログラムは `Any`）と一致し、有効で、`EnforcementStatus` が `Full`。
  - **あり（値は期待どおり。ただし、適用されているかは確認できない）**: 値は一致するが、
    `EnforcementStatus` が読めない・仕様に無い値（その値を出す）。
  - **あり（内容は期待どおり。ただし Windows ファイアウォールとしては適用されていません）**:
    中身は一致するが、`EnforcementStatus` が `Full` 以外の既知の値（理由を出す）。
  - **あり（期待と違う）**: 違う項目とその値を出す。たとえば「操作: Block」（管理者が
    遮断に変えた）、「接続元の範囲: 192.168.1.10」（狭めた）、「プログラム: 別の exe」
    （別のインストール）、「ポート: 古い番号」（ポートを変えた後）、「有効: False」、
    「適用状況: 適用されていません」（ローカルのストアにはあるが ActiveStore に無い。
    グループポリシーがローカルのルールを結合しない設定のときなど）、「適用状態: 存在
    するが適用されていません（理由: …）」（中身の違う項目と並ぶとき）。直すときは上の「既存のルールがあるとき」の手順で管理者が行う。
  - どの「あり」でも、ActiveStore のルールの出どころを `-TracePolicyStore` 付きで読み、
    種別（`PolicyStoreSourceType`）がローカル（`Local`）でなければ添える。グループ
    ポリシー・MDM（と Hyper-V のホスト ファイアウォールのそれら）は「集中管理のポリシー
    （グループポリシー）のルールです（出どころ: …）」として、値（たとえば「操作: Block」）
    はポリシーのもので直すのはポリシーの管理者になると書く。`Dynamic`・`Generated`・
    `Hardcoded`・ホスト ファイアウォールのローカル／動的は、それぞれの種別として出し、
    集中管理とは書かない。一覧に無い値は「その他（値）」。種別が取れない・空のときは
    「出どころは不明」とし、集中管理とはみなさない（出どころ `PolicyStoreSource` が空の
    ときも「不明」と出す）。ローカルのルールが無い・値が違う（違う項目とローカルの値を
    出す。その値は適用されていない）・読めないときも、それを添える。
  - 効いているルールが読めないときは、ローカルのルールがあっても「確認できない」に
    する（何が効いているか分からないため）。
  - **確認できない（理由）**: PowerShell を起動できない・時間内に終わらない（約 30 秒）・
    `Get-NetFirewallRule` などのコマンドが無い・読み込めない・権限や集中管理で読めない・
    結果を読めない、など。**読めなかったことを「ルール無し」とは表示しない。**
    「ルール無し」にするのは、ルールの検索そのものが「該当なし」と答えたとき
    （`CimJobException` で、エラー ID が `Get-NetFirewallRule` の
    `CmdletizationQuery_NotFound_*`）だけ。コマンドが見つからないとき
    （`CommandNotFoundException`。分類は同じ `ObjectNotFound`）は読み取りの失敗にする。
- 同じグループ（`-Group <identifier>`）に名前の違うルールがあれば、その件数も出す
  （別の名前で作ったルールの手がかり）。中身は管理者が確かめる。グループを読めなかった
  ときは 0 件とはせず、「確認できませんでした」と出す。
- 「再確認」が失敗した（応答が無い・形が違う）ときは、前回の結果を消してエラーだけを
  出す（古い「期待どおり」「ルール無し」を今回の結果と読み違えないため）。
- **ルールがあることと、LAN の端末から接続できることは同じではない。** セキュリティ
  ソフトのファイアウォール、そのポートを遮断する別の名前のルール（集中管理で配られた
  ものも含む。ここで確かめるのはこの名前のルールだけ）、ルーターや Wi-Fi の設定
  （端末間の通信を遮る機能など）でも遮断される。接続できるかは、実際に別の端末から
  開いて確かめる。
- 表示は、待ち受け中のサーバーの同じ snapshot（`generation`）と比べた結果だけを出す。
  確認の途中で適用やポートの変更があった古い応答は表示しない。
- 仕組み（保守者向け）: Tauri コマンド `firewall_rule_status`（admin 専用・読み取り・
  REST なし）が、`%SystemRoot%` 配下の Windows PowerShell に固定のスクリプトを
  `-EncodedCommand` で渡し、`Get-NetFirewallRule` / `Get-NetFirewall*Filter` の結果を
  既定（PersistentStore）と `-PolicyStore ActiveStore -TracePolicyStore` の両方について
  JSON で受け取る。ActiveStore の側には出どころ（`PolicyStoreSource` /
  `PolicyStoreSourceType`）と `EnforcementStatus` の生の値（`MSFT_NetFirewallRule` の
  `uint16[]`）が付く。スクリプトは最初に `Get-Command` でコマンドがあるかを確かめ、
  無ければ何も読まずに失敗として終わる。

#### ファイアウォールで許可する（段階 2、UAC で昇格）

状態の欄の「ファイアウォールで許可する」「許可を外す」（admin・デスクトップのみ）は、
本体 exe の隣にある helper（`<本体の exe 名>-fw-elev.exe`）を UAC で昇格して起動し、
実行ファイル単位のルール 1 本だけを足し外しする（[ADR-0021](../adr/0021-firewall-elevated-helper.md)）。

- **前提: Program Files の下に perMachine でインストールしたとき**だけ働く。インストーラは
  `pnpm --filter admin-template tauri:build:windows` で作る（helper を先にビルドして
  本体の隣に同梱する。素の `tauri build` では helper が入らない）。このスクリプトは `--features embed-ui` も付けるので、LAN 向けの Web UI も入る（下の「`embed-ui` フィーチャー」）。作るのは NSIS のインストーラ
  だけで、MSI には対応しない（ルールを外すアンインストールのフックが NSIS にしか無い）。テンプレートの既定の
  `installMode` は `perMachine`。portable・per-user・移動したコピー・`tauri dev` では
  「前提が無い」になり、上の段階 1 の情報（コピーするコマンド）を使う。
- インストール時にはルールを作らない。アンインストール時は、このアプリが作ったルールだけを
  helper が外す。外せないとき（管理者が変えたルールなど）はアンインストールを止めず、
  アンインストールの詳細にルール名（`<identifier>.lan.tcp.program`）と手で外す方法を出す。

### 別の端末からの接続確認

「ルールがある」と「届く」は別なので、実際に別の端末から開いて確かめる欄を、
ファイアウォールの欄とは別に設けている（Issue #219 段階 1 の PR-C。設計は
[lan-reach-check-design](../design/lan-reach-check-design.md)）。OS に依らず、
稼働中・loopback 以外・IPv4 の待ち受けのときに出る。

1. 設定 > サーバ・接続で LAN を有効にして（待受アドレス「LAN に公開」）保存・適用する。
2. 「別の端末からの接続確認」で、確認に使うアドレス（稼働中の URL の候補。複数あれば
   選ぶ）を選んで「確認用の URL を発行」を押す。URL と QR コードと残り時間が出る。
3. 同じネットワークのスマートフォンなどで QR を読み取る（または URL を開く）。端末の
   ページ（`/reach`）は「記録しました」などの短い結果だけを出す。ログインはしない。
4. PC の画面は、確認待ちの間だけ 2 秒おきに状態を読み直し、「別の端末から到達を
   確認しました」と、時刻・接続元 IP・使った URL を出す。

**保証すること**: その時刻に、その接続元 IP の端末から、その待ち受け（ポート）へ
要求が届き、サーバーが受け付けたこと。根拠はサーバー側で観測した値だけ（サーバーの
時計・ソケットの接続元。`X-Forwarded-For` などの自己申告は使わない）。

**保証しないこと**（画面にも書く）:

- ほかの端末から届くこと（別のサブネット・VLAN・VPN の端末は別）。
- いまも届くこと。確認から 1 時間たつと「時間が経っています」と弱い表示になる。
  待受の設定を変える（保存・適用で待ち受けが替わる）と、結果は消えて「未確認」に戻る。
- 経路の途中の機器の設定がすべて正しいこと。
- このPC自身で開いたアクセスは、別の端末の確認として数えない（「このPC自身からの
  アクセスがありました」と出て、確認待ちが続く）。
- 期限（5 分）内にアクセスが無かったことは、届かないことの証明ではない。画面は
  「期限内に別の端末からのアクセスはありませんでした」と出し、同じネットワークか・
  ファイアウォール（Windows では上の 2 つの欄）・独自のファイアウォールを持つ製品・
  Wi-Fi のアクセスポイントの端末間の分離を確かめるよう案内する。

ほかの決まり:

- 確認用の URL は 1 回だけ使え、同時に有効なのは 1 つ（発行し直すと前のものは使えなく
  なる）。トークンは URL の `#t=` の後ろ（フラグメント）にあり、サーバーのログ・
  プロキシ・`Referer` に残らない。端末のページはトークンを読んだらすぐ URL から消す。
- 状態を読めなかったときは「状態を読めませんでした」と出し、「未確認」とは出さない。
- 端末のページの結果は「記録しました」「このPC自身からのアクセスでした」「使えない
  URL です（期限切れ・使用済み・待受が変わった）」「URL が違います」「しばらく待って
  からやり直してください」（失敗が続いたとき。1 分に 10 回まで）のどれか。サーバーの
  情報（PC の名前・ほかの IP など）は返さない。閲覧公開のオン / オフに依らない。
- 発行できるのはこの PC の管理者の画面だけ（ブラウザ配信の管理画面には出ない）。
  確認の口（`POST /api/reach-check`）はデスクトップの組み込みサーバーにだけあり、
  `banto-serve` には無い。発行も到達も監査ログには残さない（メモリだけ）。

## 閲覧公開（ログイン無しで LAN から閲覧を許可）

表示専用アプリ（アンドン・常設ダッシュボード・展示デモ）向けに、LAN 上の
端末が**ログイン無しで閲覧画面と読み取り API だけ**を使える「閲覧公開」を
用意している（Issue #189、[ADR-0012](../adr/0012-lan-public-viewer-synthetic-session.md)）。
設定画面「サーバ・接続」→「ログイン無しで LAN から閲覧を許可する（閲覧公開）」
を ON にして「保存して適用」。

- LAN のブラウザは `/dashboard` を開くだけで **`viewer` ロールの合成
  セッション**（ユーザー名 `public`）に入る。このセッションは
  `POST /api/auth/grant/publicViewer` で受け取る（資格情報なしのセッション発行
  「grant」の 1 種類目、[ADR-0017](../adr/0017-credential-less-grant.md)）。ヘッダの「ログイン」から通常の
  アカウントでログインすれば編集系 UI に切り替わる。
- 書き込み（作成・更新・削除・インポート）は従来どおりログイン必須。合成
  セッションからの書き込みは REST が 403 で拒否し `denied` として監査する。
- 公開される画面は `src/lib/navigation.ts` の `publicViewer: true` を付けた
  項目だけ（テンプレート既定は dashboard と items）。データ面の境界は RBAC
  の `viewer` ロールそのもの（viewer に見せたくない読み取りは閲覧公開ではなく
  ロール床で絞る）。
- ログイン不要モード（M11）と LAN アクセスは閲覧公開 ON のときだけ併用できる
  （書き込みはデスクトップだけ、閲覧は LAN 全体、が表示専用アプリの標準形。
  手順は [no-login-app.md](no-login-app.md)）。
- **LAN 上の誰でも閲覧できる**設定なので、下記「セキュリティ注意」の信頼できる
  LAN 限定の前提はそのまま。

## `banto-serve`（Tauri不要の開発用バイナリ）

```sh
pnpm --filter admin-template build   # apps/admin-template/build を生成
cargo run -p admin-template-core --bin banto-serve --features embed-ui
```

Tauriを起動せずにREST + 静的配信のフルスタックを試せる（`--features
embed-ui`を省略すると組み込みのプレースホルダページを返す）。環境変数:

| 環境変数                | 既定                    | 内容                                                                                                                                                                                                                    |
| ----------------------- | ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `PORT`                  | `8721`                  | 待ち受けポート                                                                                                                                                                                                          |
| `BANTO_BIND`            | `0.0.0.0`               | バインドアドレス                                                                                                                                                                                                        |
| `BANTO_DB`              | `./banto-dev.sqlite3`   | DB。`postgres://` URL にすると PostgreSQL 経路（[database-backup.md](database-backup.md)）                                                                                                                              |
| `BANTO_ATTACHMENTS_DIR` | （SQLite では使わない） | `BANTO_DB` が PostgreSQL のとき**必須**。添付ファイルの保存先の親ディレクトリで、DB ごとに `pg_<ホスト>_<ポート>_<DB名>_<ハッシュ>` のサブディレクトリを作る。SQLite では使わず、添付は DB ファイルの隣の `attachments` |
| `BANTO_VIEWER_PUBLIC=1` | 未設定                  | 起動時に閲覧公開を ON に seed する。e2e とローカル確認用                                                                                                                                                                |
| `BANTO_ALLOW_SETUP=1`   | 未設定（403）           | `POST /api/auth/setup`（初回セットアップ）を有効にする。dev/e2e 用（`e2e/playwright.config.ts`）                                                                                                                        |

詳細（PostgreSQL は `--features postgres` でのビルドが必要、`BANTO_VIEWER_PUBLIC` は
設定を永続化するので外しても OFF に戻らない等）は
`apps/admin-template/core/src/bin/banto-serve.rs` 冒頭の doc コメントが一次情報。

## `embed-ui` フィーチャー

- `admin-template-core`はデフォルトでフロントエンドを埋め込まない
  （プレースホルダページのみ）。`pnpm --filter admin-template build`で
  フロントをビルドしてから`--features embed-ui`を付けて再ビルドすると、
  実際のSvelteKitビルドが埋め込まれる。
- src-tauri（デスクトップアプリ本体）も同名のパススルーfeatureを持つ:
  `tauri build --features embed-ui`（または`cargo build -p admin-template
--features embed-ui`）を指定しないと、LANアクセス経由のブラウザには
  プレースホルダページしか返らない（Tauriウィンドウ自体の表示には影響
  しない — Webview は常にバンドルされた実フロントを表示する）。
- 配布用の`pnpm --filter admin-template tauri:build:windows`は`--features embed-ui`
  付きなので、そのインストーラにはLAN向けのUIが入る。素の`tauri build`・`tauri dev`では入らず、
  設定画面は（別の端末が開く画面が仮のページなので）URL・QRと「別の端末からの接続確認」を出さず、
  確認できない旨の注記だけを出す（`ServerStatus.uiEmbedded`、Issue #478）。

## セキュリティ注意

> ⚠️ **LANサーバ機能は標準ではHTTP（平文）です。** ログイン情報・セッション
> トークン・業務データが暗号化されずにネットワークを流れます。公衆Wi-Fi・
> ゲストネットワーク・信頼できない端末が混在するネットワークでは有効化
> しないでください。拠点をまたぐ利用やVPN外での利用が必要な場合は、下記の
> リバースプロキシでTLS終端してください。

- v1は「信頼できるLAN内でのHTTP + トークン認証」という割り切り。TLSは
  未実装（v2以降で検討、[ADR-0003](../adr/0003-tls-via-reverse-proxy.md)）。
  **信頼できるLAN以外では有効化しないこと。**
  HTTPのみのため、ログイン情報やセッショントークンは平文でLAN内を流れる。
- 認証はargon2id資格情報ストア + 初回セットアップ実装済み
  （`crates/banto-admin-services/src/users.rs`。固定パスワードのデモ実装
  ではない）。セッショントークンは絶対8時間/アイドル1時間で自動失効し、
  ログインは5回連続失敗で60秒ロックアウトされる（いずれも
  `banto-server`の`TokenPolicy`/`RateLimitPolicy`で変更可能）。
  Tauriウィンドウのセッションと LANブラウザ側（REST/SSE）のセッションは
  独立したトークン空間。
- セッショントークンはインメモリ保持のため、**サーバ（デスクトップアプリ/
  常駐プロセス）を再起動すると全セッションが失われ、再ログインが必要**になる。
  「ログイン状態を保持（Remember me）」の30日/7日は無停止運用時の上限であり、
  端末を毎日再起動する運用ではその都度セッションが切れる（v1 の受容済み仕様。
  [roadmap.md](../roadmap.md) の未決事項一覧を参照）。

## 同時書き込みとSQLite（WAL）

デスクトップアプリと組み込みサーバは**同一プロセス内で動き、単一の
SQLite コネクションプールを共有する**（Tauriコマンドと REST ハンドラは
同じ `ItemsService` 等 = 同じプールへの `Clone` ハンドルを使う）。したがって
Tauriウィンドウからの書き込みと LANブラウザからの書き込みは**その1つの
プールでシリアライズ**され、プロセスをまたぐ書き込み競合は起きない。DBは
**WAL モード**（`crates/banto-storage/src/sqlite.rs`）で開くため、読み取りは
書き込みをブロックせず、複数の LAN クライアントが同時に閲覧しても問題ない
（SQLite の WAL は「同時に多数の読み取り + 1つの書き込み」を許す）。

注意: 同じ SQLite ファイルに**別プロセスから同時アクセスしない**こと
（例: 稼働中のアプリと並行して 2つ目の `banto-serve` や外部ツールを同じ
DB に向ける）。WAL が保証するのは単一ライタまでで、別プロセスの2つ目の
ライタは `SQLITE_BUSY` を招きうる。バックアップ/リストアはこのシリアライズ
の一部として同一プロセス内で扱う（M17、`VACUUM INTO`。
[database-backup.md](database-backup.md)）。

## リバースプロキシでのTLS終端（Caddy 例）

TLSが必要な環境では、Banto自体はHTTPのまま `127.0.0.1` バインドに絞り、
前段のリバースプロキシでTLSを終端する（[ADR-0003](../adr/0003-tls-via-reverse-proxy.md)）。
[Caddy](https://caddyserver.com/) なら自己署名/内部CA証明書の自動発行込みで
以下の数行で済む:

```
# Caddyfile — https://<このマシンのホスト名>:8443 で待ち受けて Banto へ転送
{
	local_certs   # 内部CAで自動発行（社内CA/正規証明書があればこのブロックは不要）
}

:8443 {
	reverse_proxy 127.0.0.1:8721
}
```

設定画面のバインドアドレスは `127.0.0.1 のみ` にする（`0.0.0.0` のままだと
プロキシを迂回した平文HTTPでも届いてしまう）。

注意: プロキシ経由では、Bantoから見た接続元が全部プロキシのIP
（127.0.0.1）になるため、ログインレート制限の per-IP 次元
（`banto-server` の `RateLimitPolicy.max_ip_failures`、既定20回/60秒）が
**全クライアント合算**で発火するようになる。クライアント台数が多い環境では
しきい値を引き上げるか、per-account 次元（既定5回）だけに頼る設定を検討
する（`X-Forwarded-For` の信頼はv1では未実装 — 偽装可能なヘッダを無条件に
信じないための割り切り）。

### プロキシ越しの grant（資格情報なしのセッション発行）の運用ルール

資格情報なしのセッション発行（grant、[ADR-0017 §6](../adr/0017-credential-less-grant.md)）を
プロキシ越しに使う場合の運用ルール（Banto が技術的に強制できるものではない。
同一ホストのプロキシの後ろでは接続元がすべてループバックに見えるため、
`require_loopback_peer` は何も守らない）:

- 外部公開（プロキシから外へ出す）の前に、管理者相当の grant（派生アプリの
  試運転など）はロックダウンしておく。
- 再試運転の間も `/api/auth/grant/{kind}` をプロキシから外部へ公開しない
  （プロキシ側でそのパスを遮断するか、試運転中はプロキシを止める）。

プロキシが `Host` を書き換える設定や共有キャッシュを前段に置く構成での CSP の注意は
[conventions.md §6](../conventions.md)（`request_is_loopback_local` の項）。

## PWA（ホーム画面に追加 / インストール）

LANブラウザ配信は Web マニフェスト（`static/manifest.webmanifest` + アイコン）
を同梱しており、ブラウザから「ホーム画面に追加」/「インストール」でアプリの
ように起動できる（工場のタブレット等での常用向け）。オフライン対応（Service
Worker）は入れていない。**ただしブラウザはセキュアコンテキストでしかインストールを
提供しない** — 標準の平文HTTP LAN 配信では機能せず、上記のTLSリバースプロキシ
配下・`localhost`・GitHub Pages デモ（HTTPS）でのみインストール可能になる。
アプリ名を変えるときは [`rename.mjs`](../../scripts/rename.mjs) が manifest の
`name`/`short_name` も追随させる（アイコン画像は差し替えが必要 — rename が
触らない資産。[rename.md](rename.md)）。
